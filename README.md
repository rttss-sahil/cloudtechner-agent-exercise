# CloudTechner — Agent Setup Exercise

Q&A agent over a `runbooks/` corpus + evaluation harness. Pure Python stdlib, no
install required, runs on Python 3.9+.

```
answer_question(question: str) -> dict
   -> {"answer": str, "cited_doc_ids": list[str], "confidence": "high"|"medium"|"low"|"no match"}
```

`confidence == "no match"` (with empty citations) is a legitimate, expected answer
when no runbook actually applies — citations are never forced onto a
closest-sounding doc.

## Layout

| Path | Purpose |
|---|---|
| `cloudtech_rag/` | package: `agent.py` (entry point), `retrieval.py` (index + scoring), `loader.py`, `config.py`, `__main__.py` |
| `main.py` | root entry point mirroring `answer_question` + CLI |
| `harness.py` | evaluation harness (4-bucket scoring, FR-6/FR-7) |
| `examples.json` | official 5 questions + adversarial self-tests with expected doc ids |
| `runbooks/` | **MOCK corpus** — per HR guidance ("use mock data"), generated by `scripts/make_sample_corpus.py`. 12 docs with deliberate near-duplicate traps (same structure, different service/failure mode). |
| `output/harness_output.txt` | harness report (latest run) |
| `WRITEUP.md` | design rationale: why this retrieval, what it handles / doesn't |
| `FRD.md` | functional requirements document |
| `scripts/make_sample_corpus.py` | generates the synthetic smoke-test corpus |

## Quick start

```bash
# 1. (one-time) HR confirmed to use mock data: generate the mock runbooks corpus
python3 scripts/make_sample_corpus.py

# 2. ask a question
python3 main.py -q "checkout-api is running hot on CPU - what should I check first?"
# or
python3 -m cloudtech_rag -q "We're seeing 'too many connections' errors on checkout-api"

# 3. run the evaluation harness (loads examples.json)
python3 harness.py
# report is printed and written to output/harness_output.txt
```

## Using the agent programmatically

```python
from cloudtech_rag import answer_question

answer_question("How do I safely roll back checkout-api to a previous version?")
# {"answer": "...", "cited_doc_ids": ["RB-005"], "confidence": "medium"}
```

Run against a different corpus:

```python
from cloudtech_rag import Agent
agent = Agent("/path/to/runbooks")
agent.answer_question("...")
```

## Evaluation harness

`harness.py` classifies every `(question, expected)` case into four buckets:

1. **correct** — cited the right doc(s)
2. **wrong** — cited the wrong doc(s)
3. **correct no-match** — correctly returned no match (expected doc = none)
4. **incorrect no-match** — returned no match when a doc actually applied

Score = (correct + correct no-match) / total. Exit code 0 only on a full pass.

`examples.json` ships with the 5 official questions plus self-added traps:
wrong-service near-duplicates (payments/inventory vs checkout), a severity
process lookup, and out-of-corpus no-match cases. Expected doc ids line up with
the assignment's examples: CPU→RB-001, connections→RB-002, rollback→RB-005,
incident→RB-011, customer comms→RB-012.

## Tuning

Thresholds (`MATCH_FLOOR`, `CONF_HIGH`, `CONF_MED`) and the optional
`EXTRA_SERVICES`/`SERVICE_ALIASES` live in `cloudtech_rag/config.py`. They are
calibrated to the mock corpus; if you swap in different runbooks, run
`python3 harness.py`, read the per-case report, and adjust the cutoffs. No code
changes needed.

## Requirements

Python 3.9+ standard library only. No pip install, no model downloads, no network.

## Cloudflare Workers/Pages deployment (`worker/`)

The whole engine is **stateless**: the corpus gets bundled into the Worker at build
time, so there is no KV/D1/filesystem at runtime.

- TypeScript port of the same retrieval engine, verified byte-for-byte against the
  Python one: `npm run parity` → expect `11/11 cases match`.
- `POST /api/answer` `{"question": "..."}` → `{answer, cited_doc_ids, confidence}`
- `GET /api/answer?q=...&debug=1` → also returns the ranked diagnostics
- `GET /` → served from `public/` (a small Pages-style UI) via the `ASSETS` binding

```bash
cd worker
npm install
npm run parity     # sanity: TS vs Python engines agree on all cases
npm run dev        # build:data + wrangler dev (local server on :8787)
npm run deploy     # build:data + wrangler deploy -> workers.dev URL
```

Layout: `src/{index,agent,retrieval,config,types}.ts`, `src/data/runbooks.ts`
(auto-generated, don't edit), `public/index.html`, `scripts/{build-data,parity}.mjs`.

**Want Cloudflare Pages instead of a Worker?** Keep `public/` as the static site
and move the handler into `functions/api/answer.ts`:

```ts
import { Agent } from "../src/agent";

export const onRequest: PagesFunction = async ({ request }) => {
  const body = await request.json() as { question?: string };
  const agent = Agent.fromBundled();
  return Response.json(agent.answerQuestion(body.question ?? ""));
};
```

Same code, same engine — the handler is `request`-shaped so it drops into either
runtime. When the real runbooks arrive, swap `../runbooks` and re-run
`npm run parity`; if a case flips, tune `src/config.ts` thresholds.
